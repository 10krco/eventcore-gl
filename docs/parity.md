# EventCore 2.1.0 feature inventory

Each row links to executable Gleam acceptance evidence and a passing CI run. The owning Tiber task records delivery and final CI evidence. Use the task ID with `tiber show` to read its checklist.

The comparison uses the [published crate](https://crates.io/crates/eventcore/2.1.0), the [release manifest](https://github.com/jwilger/eventcore/tree/fea3e386cce904e9ef9b76cd303926870d04a692/eventcore/Cargo.toml), and the release's supporting crates and tests. It covers the default macros, optional PostgreSQL and SQLite integrations, experimental modeling and model checking, and the memory, filesystem and testing crates. Source links are pinned to the release commit.

With SQLite and PostgreSQL, an empty append succeeds without checking expected
versions or opening a database transaction. A nonempty batch still checks every
registered participant. SQLite and PostgreSQL tests exercise both paths.

Open the journal with `RustRelease` to reproduce the published fork rules.
The release tests exercise initial claim events, read-only stream claims,
empty appends, and ordinary appends that close forks. The default
`FullBranches` policy requires a recorded resolution and supplies each
branch's events through its current head.

## Compatibility profile

Use `RustRelease` for filesystem fork reconciliation. The normal filesystem
open uses `FullBranches`. The [journal architecture](../ARCHITECTURE.md) and
[reconciliation decision](decisions/0023-filesystem-release-reconciliation.md)
describe both policies.

Use an explicit event-kind filter for a projection that consumes one event
type. The Gleam event store and projection APIs use caller-supplied codecs and
filters. The Rust APIs derive the discriminator from the event type when a
legacy projection omits it.

The release's Rust macros and contract test macros are represented by typed
Gleam functions, compiler rejection fixtures, and reusable runtime assertions.
Storage formats and toolchains are native to their respective implementations.
